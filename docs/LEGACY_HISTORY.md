# Тренировочный перенос истории старой CRM

## Через браузер

1. Установить опубликованное обновление обычной кнопкой CRM.
2. Открыть «Справочники и настройки» → ссылка в верхнем меню «Перенос старой CRM», либо `/management/legacy/`.
3. Выбрать новый подготовленный ZIP истории версии 2. Для повторной тренировки проверить режим «Очистить тренировочные данные перед загрузкой» (при уже загруженной истории выбран заранее), ознакомиться с сохраняемыми исключениями и подтвердить режим. Это отдельный пакет, не ZIP библиотеки и не SQL Server .bak.
4. Нажать «Загрузить тренировочную историю». Работа продолжается в отдельном процессе сервера, окно можно закрыть. Не запускать обновление программы до результата.
5. После завершения скачать отчёт. Для старых договоров/платежей выбрать соответствующий период: журналы первоначально показывают сегодня.

Доступ к загрузке, состоянию, отчёту и скачиванию исходных записей — только у действующего суперпользователя. Пакет и отчёт содержат реальные данные, не публиковать их в Git/открытых каталогах.

До записи создаётся резервная копия SQLite в закрытом каталоге рядом с базой: `legacy-imports/UUID/before.sqlite3`. Импорт целиком выполняется в одной транзакции. Временный ZIP удаляется после обработки; резервная копия и состояние остаются. Ошибка проверки/записи отменяет эту загрузку. Повтор того же пакета сохраняет ручные правки и не добавляет дубликатов; после удаления импортированных записей повтор блокируется. Другой снимок того же источника требует отдельной сверки. Это не автоматическая синхронизация со старой CRM.

Режим «Очистить тренировочные данные перед загрузкой» разрешён владельцем: перед новым импортом удаляются Договоры, Задачи, Финансы, Заказчики, Туристы и остальные рабочие справочники. Библиотека, Шаблоны задач, Операции, Валюты, Города вылета, Страны и учётные записи пользователей сохраняются. Вспомогательные типы сохранённых шаблонов восстанавливаются; старые фильтры журналов очищаются без выхода из аккаунтов. Очистка и импорт атомарны. Для этого режима нужен новый пакет версии 2; изменённые правила нельзя применить повторной загрузкой старого пакета без очистки. Не выключать старую рабочую CRM для этой тренировки.

## Согласованные правила

- Денежные суммы — рубли; подтверждено владельцем. Старый справочник валют содержит несогласованные названия/коды и не используется для пересчёта.
- Итог — SUMMA из шапки. Строки сохраняются с исходными суммами. Разницу хранит отдельное поле договора; она явно показана в карточке и включена в журнальные итоги. Последующие изменения строк меняют общую сумму с сохранением исходной разницы.
- ADD_SUM_OPLATY_TO — накопленная фактическая оплата ТО за вычетом возвратов. Включена в себестоимость вместе с будущими новыми операциями. ADD_DATE_OPLATY_TO означает полный расчёт; без даты сумма промежуточная. По уточнению владельца создаётся одна перенесённая финансовая операция «Тинькофф р/с» на эту сумму (при отрицательной — возврат). Дата — ADD_DATE_OPLATY_TO, либо дата договора, если она отсутствует; признак полной оплаты в последнем случае остаётся пустым. Начальный агрегат при этом нулевой, двойной учёт исключён. Это перенос накопленной суммы, не восстановление отдельных старых платежей.
- Клиентские платежи: SUM_RUB, отрицательное значение → возврат клиенту с положительной абсолютной суммой. Направление — приход, статус — оплачено (ID_SUB_PRIZNAK_MANY=1). ID_PRIZNAK_MANY задаёт наличный/безналичный признак, не статус. Сохраняется исходный плательщик, даже если он отличается от заказчика договора.
- Положительные платежи без найденного договора по решению владельца остаются в отчёте; в финансовый журнал не загружаются. Нулевые записи сохраняются в исходном архиве/отчёте, без создания денежного движения. Это явные исключения сверки, не потерянные данные.
- Если название исходного счёта/способа оплаты отсутствует, создаётся отдельная пометка по его исходному коду. Название не угадывается; соответствие можно уточнить позже.
- Корзина исключена. Исключение — необходимые удалённые заказчики, связанные с переносимыми действующими документами/платежами/задачами; их восстановление согласовано. СЧЕТ и ПКО исключены.
- Счётчики взрослых/детей для старых строк рассчитываются только при известных дате рождения и дате поездки; граница — 18 лет. Исходные даты сохраняются, недостающие даты не угадываются.
- Туристы заполняют справочник Tourist и связываются со строками. Одинаковые нормализованные ФИО, дата рождения и паспорт повторно используют карточку. Исторические снимки в строках сохраняются отдельно. Их исходные поля раскрываются в карточке. Редактирование этих исторических паспортных снимков пока не реализовано; суммы/описания строк редактируются обычным способом.
- Действующие реквизиты и контакты — в карточке заказчика. Исторические реквизиты договора сохраняются отдельно и раскрываются на вкладке заказчика. Остальные исходные поля сохранены в защищённом архиве, включая дополнительные поля, время задач и примечания.
- Задачи привязываются к исходному заказчику. По новому правилу невыполненные связываются с последним его договором по дате/времени источника (при равенстве — больший исходный ID); выполненные остаются общими. При отсутствии договора невыполненная задача также остаётся общей. Сохраняются даты, описание/результат, план/выполнение; исходные служебные поля доступны в архиве. Исторические сотрудники имеют отключённый вход и непригодный пароль; их старые пароли/интеграционные секреты вообще не экспортируются.
- Используемые основные справочники сопоставляются по нормализованному названию. Исходные ID географических справочников не объявляются кодами Турвизора; старые ID остаются в архиве, новые отсутствующие названия получают отдельный префикс legacy.
- Вложения — только библиотека, уже отдельным пакетом; этот пакет не содержит файлов или броней ТО.

## Проверка

Отчёт содержит количества, суммы, исходные ID исключений и замечания: разницы шапки/строк, обратные даты поездки в источнике, отсутствующие названия способов оплаты, различие плательщика и заказчика и сокращённые отображаемые поля. Полный текст исходных полей сохранён независимо от ограничения длины новой формы.

В карточке импортированного договора — отметка «Старая CRM», исходные поля для скачивания, разница сумм и накопленная оплата ТО. В админке «Legacy records / исходные записи» можно найти исходную таблицу и ID. Это технический архив для сверки, он не заменяет рабочие карточки.

Перед окончательным переносом проверить на выбранных примерах незакрытые договоры, долги, возвраты, туристов, реквизиты, себестоимость и задачи. Ошибочные исходные даты и неизвестные названия справочников не исправляются автоматически.

## Подготовка и CLI

`scripts/export_legacy_history.py OUTPUT.zip` работает только с изолированной базой legacy_crm в READ_ONLY. Подключение — локальный SQL Server, пароль только из MSSQL_SA_PASSWORD. Выгрузка явно ограничена согласованными таблицами; MANAGERS содержит только ID и имя. Поля сотрудников с паролями/настройками интеграций исключены. Дата снимка в сценарии должна обновляться при подготовке финальной копии.

`python manage.py import_legacy_history PACKAGE.zip --dry-run` проверяет структуру, связи и подготовку целевых полей без записи. Без --dry-run импортирует атомарно (для CLI резервную копию создать отдельно; браузерный процесс делает её автоматически). --actor задаёт пользователя журнала. --job — внутренний фиксированный режим фонового запуска, не требует root.

ZIP до 8 МБ, единственный history.json до 100 МБ, формат aborigen-legacy-history-v2 (старый v1 поддерживается только без очистки). Отдельные записи ограничены по размеру, проверяются исходные ключи, ссылки и согласованный состав. Исходные записи сохраняются в LegacyRecord с ключом `(источник, таблица, ID)`; библиотека использует отдельный раздел журнала. Эти данные и вложения библиотеки входят в обычное резервное копирование базы.

Уточнения полей и общая таблица способов оплаты: [LEGACY_REVIEW.md](LEGACY_REVIEW.md). Справочник PRIZNAK_DOCUMENTS включён в пакет v2; ID статуса документа не смешивается с кодом финансового счёта.

После обновления от 26.10.2026 результат задачи хранится отдельно в `Task.result` и заполняется из `REZULTAT_CONTACT`; `PRIMECHANIE` остаётся описанием. Миграция 0033 также разделяет уже загруженные данные через сохранённые исходные записи. Ручные изменения описаний сохраняются; повторная загрузка пакета для этого не нужна.
