# ETA: фоновый исполнитель и официальная почта

## Что сделано и где граница готовности

Существуют `ETAApplication`, `ETAExport` и протокол v1. Они сохранены: очередь, аренда исполнителя и однократная отметка начала подачи добавлены в `ETAApplication` миграцией 0041. `ETAOfficialNotice` хранит только полученные официальные сообщения и их доказательства, а не параллельный журнал заявлений.

Обычный путь больше не требует JSON: пользователь готовит сведения в CRM, выбирает готовые задания → «Оформить ETA» → исполнитель возвращает фактическую сводку → пользователь читает условия, проверяет данные/сбор и подтверждает в CRM → исполнитель повторно проверяет актуальное разрешение и продолжает тот же браузер. Резервные файлы задания, результата и разрешения остались в сворачиваемых разделах.

**Это подключаемая инфраструктура, ещё не включённая в рабочей CRM.** Не настроены серверные секреты/IMAP и проверенная карта актуальной формы. Из среды разработки официальный портал вернул HTTP 403 CONNECT tunnel failed. Нет достоверно проверенных живых селекторов, текущих условий, типов писем и финальной кнопки. Они не выдуманы. Поставляемая `portal-map.example.json` имеет `verified=false` и останавливает исполнитель до настройки. Настоящие заявления не подавались. Проверки браузера выполнялись только на локальных синтетических страницах.

### Минимальное размещение

- Существующая CRM: Django + текущая БД, защищённый HTTPS API и интерфейс. Chromium сюда не устанавливать: VPS имеет 1 ГБ ОЗУ.
- Отдельная VM/машина: Ubuntu 24.04, Python 3.12, Chromium/Playwright, 2–4 ГБ ОЗУ (лучше 4 ГБ), приватный диск. Два systemd-сервиса `eta-executor` и `eta-mail` могут работать на одной машине. Нужны только исходящие HTTPS и IMAPS 993; прямого доступа к БД нет.
- Почта: поддерживаемый IMAP SSL Яндекса `imap.yandex.ru:993`, пользователь `spo-ab@ya.ru`, отдельный пароль приложения с доступом к почте. Сервис читает INBOX в режиме readonly и BODY.PEEK: не удаляет письма и не меняет признак прочтения. Курсор UIDVALIDITY/UID сохраняется приватно; повтор доставки устраняется SHA-256 оригинала на стороне CRM.
- Для CAPTCHA необходим доступ сотрудника к **этому же** графическому сеансу браузера на машине исполнителя (локальный рабочий стол / защищённый remote desktop). Веб-трансляция браузера в CRM в эту реализацию не включена. В headless-режиме CAPTCHA останавливает работу, а не обходится. Для рабочего стола надо настроить DISPLAY/XAUTHORITY и доступ сервисного пользователя; не публиковать VNC в Интернет.

### Сохранение сессии

Между подготовкой и подтверждением остаётся открытым тот же Chromium context и страница, включая JS/DOM. Ограничение `ETA_MAX_SESSIONS` (по умолчанию 3) не выталкивает ожидающих туристов: новые подготовки ждут свободной ёмкости. Профиль cookies/storage хранится в `ETA_STATE_DIR/<application_uuid>/<batch_uuid>/chromium`, файлы 0600/каталоги 0700. После перезапуска процесса DOM не восстановим только из cookies: окончательная подача останавливается до повторного получения и согласования сводки. Перед повторным заполнением проверяется локальная и серверная отметка начала подачи. Старый профиль с другой версией данных автоматически не переиспользуется.

## Настройки, которые нужны от владельца

1. Машина исполнителя и способ установить на ней Python/Chromium, доступ сотрудника к её браузеру для CAPTCHA. Из этой машины портал должен открываться; блокировку разработки проверять отдельно.
2. На CRM и исполнителе — одинаковый случайный `ETA_WORKER_TOKEN` (минимум 32 символа), на CRM и почтовом сервисе — **другой** `ETA_MAIL_TOKEN`. Генерация на сервере: `python3 -c 'import secrets; print(secrets.token_urlsafe(48))'`. Не присылать значения в чат. HTTPS сертификат CRM должен проходить обычную проверку, перенаправления API запрещены.
3. Включить в Яндексе доступ почтовых программ через IMAP и создать пароль приложения для почты. Записать его только в `/etc/eta-mail.env`, root:root 0600. При отличающейся папке входящих указать `ETA_IMAP_FOLDER`.
4. На рабочей машине снять и проверить карту **текущей официальной** формы, сводки, суммы и экрана статуса: заполнение, безопасные переходы, окончательная кнопка, признаки CAPTCHA/существующей визы, номер принятого заявления, статус и ссылка настоящего Approval Notice. Нужен также образец официального письма без пересылки для проверки формата и заголовков. Реальную подачу при этой настройке не выполнять.
5. Согласовать разрешённые официальные домены отправителя по реальным письмам и доверенный `Authentication-Results` принимающего почтового сервера. До проверки они пустые, автоматическое признание подлинности выключено; письма поступают на ручную проверку.
6. Установить обновление CRM и выполнить штатные миграции. Отдельные сервисы устанавливаются отдельно; обычный updater их не запускает и не раскрывает секреты.

### Настройки CRM `/etc/aborigen-crm.env`

```dotenv
ETA_EXECUTOR_ENABLED=1
ETA_WORKER_TOKEN=<сгенерировать на сервере>
ETA_MAIL_TOKEN=<другой случайный токен>
# Заполняются только после проверки реальных писем/политики почтового шлюза:
ETA_MAIL_OFFICIAL_DOMAINS=
ETA_MAIL_AUTHSERV_ID=
ETA_MAIL_AUTOMATIC_TRUST=0
```

С пустыми токенами API закрыт. На CRM перезапустить штатный сервис после изменения env. При `ETA_EXECUTOR_ENABLED=0` файлы остаются доступными; worker API возвращает 503. Почтовый API имеет отдельную область доступа, не выдаёт паспорта, пакеты и разрешения.

### Установка на отдельной VM

Пути предполагают checkout опубликованной CRM в `/opt/aborigen-crm`. Выполнять после настройки сервера, не на текущем VPS CRM:

```sh
sudo apt-get install python3-venv fonts-dejavu-core
sudo useradd --system --create-home --home-dir /var/lib/eta-executor eta-executor
sudo python3 -m venv /opt/eta-venv
sudo /opt/eta-venv/bin/pip install -r /opt/aborigen-crm/integrations/eta_executor/requirements.txt
sudo /opt/eta-venv/bin/playwright install-deps chromium
# Browser binary must be readable by the service account, not installed only under /root:
sudo -u eta-executor /opt/eta-venv/bin/playwright install chromium
sudo install -m 600 deploy/eta-executor.env.example /etc/eta-executor.env
sudo install -m 600 deploy/eta-mail.env.example /etc/eta-mail.env
sudo install -d -m 755 /etc/eta-executor
sudo install -m 644 integrations/eta_executor/portal-map.example.json /etc/eta-executor/portal-map.json
sudo install -m 644 deploy/eta-executor.service deploy/eta-mail.service /etc/systemd/system/
```

Заполнить env локально на сервере. Сначала `ETA_ALLOW_SUBMIT=0` (по умолчанию). Настроить/проверить карту, затем `systemctl daemon-reload` и запустить сервисы. Инструкции — подготовленный комплект, не сообщение об уже выполненной установке. Пакет `reportlab` добавлен в зависимости CRM для PDF-копии текста; на CRM нужен `fonts-dejavu-core` (в Ubuntu обычно уже есть). В контейнере без шрифта скачивание PDF вернёт понятное сообщение; EML останется доступен.

Не включать `ETA_ALLOW_SUBMIT=1` до проверки живой формы и последнего клика. Тестовый режим допускает ввод/получение сводки, но никогда не нажимает финальную кнопку. Если портал называет промежуточную кнопку “Continue”, нужно отдельно проверить её смысл: название само по себе не доказывает, что это не подача.

## Карта портала и неполные сведения

`integrations/eta_executor/portal.py` — реальный Playwright-драйвер. Карта задаёт последовательность экранов, селекторы, соответствия справочников и полей `data` протокола v1. `steps[].fields[]`: `path`, `selector`, необязательные `kind` (text/select/checkbox/radio), `values` (явное соответствие строк), `date=true` (ISO → MM-DD-YYYY). Текст вводится по символам и перечитывается после blur. Невидимые поля проверяются: кроме явно указанных служебных имён новые поля останавливают процесс.

`summary_marker`, `summary_items` и `summary[]` задают **все** строки фактической сводки. Для каждого значения: `path`, `selector`, необязательные `attribute=value`, `type` (str/int/bool/iso_date/json). Должны быть прочитаны паспорт/ФИО/контакты/даты/адрес/дополнительные поля, а не скопированы из входного JSON. Метаданные CRM (возраст, связь с родителем, признак собственного паспорта) сохраняются отдельно из задания; они не выдаются за показанные порталом поля. Пример работающей карты только для синтетической страницы находится в `scripts/test_eta_executor.py`.

`conditions`, `fee_amount`, `fee_currency`, `submit`, `application_number`, `portal_status` задают актуальные условия, фактический сбор, финальное действие и результат. `blockers` — видимые селекторы CAPTCHA/existing_visa/unknown. Новая строка сводки и неизвестное обязательное поле останавливают работу. Все условия/сводки проверяются в CRM; непосредственно перед финальным кликом повторно считываются сумма, сводка и условия.

Если адрес отеля или структурированный английский домашний адрес отсутствуют, драйвер не придумывает их: задание останавливается/возвращается на подготовку. **Автономный поиск/перевод адресов внешним агентом в этом подключении не реализован**: архитектура допускает обогащение исполнителем с источником по v1, но в комплекте только детерминированный браузерный драйвер. Для первого прохода такие поля нужно проверить в подготовке.

`status.fields` задаёт необходимые для проверки поля (например, паспорт/дата рождения/гражданство) с теми же `path`/`selector`/`values`/`date`; неизвестные элементы этой формы также останавливают процесс. `status` содержит отдельный URL и элементы безопасной проверки номера, паспорта и ФИО основного заявителя, соответствие сырых статусов и ссылку на официальный PDF. Этот путь не вызывает финальное действие подачи. Только номер без паспорта/ФИО недостаточен. Внешние POST/frames/scripts блокируются; сейчас драйвер разрешает только `eta.gov.lk` и `www.eta.gov.lk`. Если официальный поток использует другую инфраструктуру, её нужно сначала проверить и явно доработать allowlist. Переходы и скачивание документа с перенаправлением на неизвестный хост запрещены.

## API и защита повторов

Все методы POST, HTTPS, `Authorization: Bearer ...`, токены только сервер-сервер, не URL. Worker ID — стабильное имя машины, lease token — временный случайный секрет. Принадлежность результата проверяет существующий протокол v1 (пакет/договор/турист/отпечаток/разрешение). Номер ETA не заменяется автоматически.

- `/api/eta/v1/claim/` → одно задание и один турист из существующего пакета; действие prepare/submit/status.
- `/api/eta/v1/sessions/` сообщает исполнителю об отозванных/завершённых сессиях; они закрываются и освобождают ёмкость. Новая версия пакета получает отдельный профиль.
- `applications/<uuid>/heartbeat/` продлевает аренду на 5 минут.
- `applications/<uuid>/begin-submission/` проверяет активное человеческое разрешение, источник CRM, фактические отпечатки сводки/условий, сумму/валюту и атомарно ставит однократную отметку **до** клика. Повтор запрещён даже если ответ API потерялся.
- `applications/<uuid>/result/` принимает один результат v1 исключительно для текущей аренды.
- `/api/eta/v1/mail/` принимает ограниченный base64 EML, без доступа к заданиям.

Если процесс погиб после начала подачи, истёкшая аренда переводится только в проверку статуса — не в отправку. Потерянная подготовка останавливается; сотрудник решает CAPTCHA/проверяет сессию и нажимает продолжение в CRM. Локальный fsync-журнал не даёт повторить финальный клик при рестарте. Если CRM приняла разрешение, а ответ не дошёл, браузер не пытается разрешить/отправить заново. Определение статуса/письмо восстанавливают номер принятого заявления. Возврат на подготовку заблокирован, пока lease активен или подача начата. Обновление CRM не отменяет сохранение пришедшего результата: сопоставление идёт с неизменяемым переданным снимком.

После успешной подачи проверка статуса ставится через 10 минут. Получение писем — каждую минуту; отсутствие письма не является поводом новой подачи. CAPTCHA/изменённый ответ/ошибка чтения статуса требуют вмешательства и видны в CRM. Если доступен официальный PDF Approval Notice, сохраняется именно он; драйвер не создаёт собственное одобрение. Содержание PDF автоматически OCR не проверяется: соответствие проверяется по идентифицированному экрану портала и метаданным, перед передачей туристу документ нужно просмотреть.

## Письма, подлинность и документы

Оригинал EML ограничен 2 МБ, результат браузера — 12 МБ с ограниченным PDF; неизвестные дампы протокола не принимаются. Почтовый курсор отмечает UID только после ответа CRM; повторное чтение безопасно. Слишком большие письма не загружаются в БД, требуют проверки в почтовом ящике. Первый проход читает последние 200 писем (настраивается), а не весь архив; последующие — новые. Почтовый ящик не очищается.

Типы: receipt (подтверждение приёма), approval (ETA APPROVAL NOTICE), referral (дополнительное рассмотрение/иммиграционная служба), unknown. Смешанный/пересланный/неизвестный формат — ручная проверка. Парсер поддерживает явно подписанные номер ETA, Passport Number, Surname/Family Name, Given/Other Names. Для отличающегося реального формата требуется проверенный образец и расширение парсера с тестом, не угадывание.

Точное совпадение **основного** заявителя: номер ETA + паспорт + фамилия + имена из замороженного пакета. Если отправка началась, но номер не дошёл, допускается восстановить номер из однозначного письма с точным паспортом/ФИО; неоднозначность сохраняется для проверки. Раздел Dependents/Children excluded из сопоставления; ребёнку с собственным паспортом требуется собственное сообщение/официальный документ. При нескольких совпадениях ни одно не одобряется автоматически.

Автоматическая подлинность по умолчанию выключена. При включении необходимы официальный домен From и **первый** Authentication-Results с настроенным authserv-id принимающего сервера и DKIM=pass с соответствующим header.d. Более глубокий совпадающий заголовок не принимается. Перед включением нужно убедиться, что почтовый шлюз всегда добавляет собственный Authentication-Results и удаляет поддельные входящие заголовки с этим authserv-id; иначе оставлять ручную проверку либо подключать проверяющий шлюз. Совпадение строки From не является доказательством.

Неоднозначные письма: `/eta/notices/`. Пользователь с правом изменения ETA может проверить оригинал и принять письмо в CRM, но точное совпадение основного заявителя всё равно обязательно. Неизвестный тип/противоречивые идентификаторы принудительно не одобряются: нужно уточнить сообщение/парсер. Не хранить паспортные данные в issue/чатах/обычных логах.

В карточке туриста → «Документы ETA»: безопасный текст, скачивание исходного `.eml`, PDF-копия **полученного** текста. HTML из письма никогда не исполняется: нет внешних изображений, скриптов и активных ссылок. PDF содержит SHA-256 оригинала; неподтверждённое письмо/receipt помечается NOT AN ETA APPROVAL. Это копия реального письма, а не новое официальное разрешение. Получение acknowledgement никогда не переводит туриста в «Одобрено» и не понижает ранее полученное одобрение/referral. Документы доступны только при наличии существующих прав чтения договора/туриста/заказчика/ETA. История аудита содержит только UUID и этапы.

### Хранение

EML, безопасный текст и PDF портала находятся в существующей БД, входят в её штатные резервные копии; браузерные профили — на отдельной машине исполнителя, приватно. Утвердить срок хранения и резервирование профилей/EML с владельцем; автоматическое удаление активных сессий не включено. Контролировать свободное место, завершённые профили удалять только после проверки результата. Пароли и bearer-токены не попадают в репозиторий, UI и JSON резервного экспорта.

## Проверка без реальных заявлений

```sh
.venv/bin/python manage.py test crm.test_eta crm.test_eta_live --noinput
.venv/bin/python manage.py test --noinput
.venv/bin/python manage.py makemigrations --check --dry-run
# Only local synthetic HTTP pages, system Chromium in this development environment:
ETA_TEST_CHROMIUM=/usr/bin/chromium .venv/bin/python -m unittest scripts.test_eta_executor -v
```

Проверяются существующий v1, роли токенов, lease, конкурирующий/повторный запуск, отзыв/изменение сведений/суммы, однократная подача, неизвестный результат, письмо приёма/одобрения/referral, несоответствие паспорта, Dependents, поддельный Authentication-Results, безопасный HTML/PDF, доступ к EML и резервный интерфейс. Живой портал, финальная подача и настоящий ящик не использовались.

Результат проверки этой реализации: **339 тестов Django прошли**, включая 22 новые проверки транспорта/почты; **9 браузерных проверок Playwright прошли** на локальном синтетическом сервере. `manage.py check`, отсутствие пропущенных миграций и `git diff --check` проверены. Эти результаты не заменяют настройку и проверку живого портала/IMAP.
