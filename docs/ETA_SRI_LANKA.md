# ETA Шри-Ланки: подготовка и обмен v1

Реализован первый этап: кнопка в существующем договоре, выбор туристов, подготовка/проверка сведений, один JSON задания на выбранных туристов, импорт результатов по каждому туристу, согласование фактической сводки и сборов и сохранение Approval Notice. Оформление на портале и поиск адресов в этой версии не выполняются: это задания будущему исполнителю. Обычный чат ChatGPT не является серверным обработчиком CRM.

В разработке выполнялись только попытки чтения публичных страниц официального портала; соединение из среды не установилось. Текущие поля/условия портала независимо не проверены. Ни одной реальной заявки не отправляли, оплат не производили. Правила возраста детей из запроса пользователя используются как проверяемые ограничения подготовки, а не как утверждение о неизменных условиях портала.

## 1. Архитектура и поля

CRM: Django 5.2, существующие модели Contract, ContractLine, Tourist, Customer. Договоры и туристы связаны через ContractLine; строки с одним туристом дедуплицируются. Роли/CSRF/история AuditEvent используются штатные. Рабочая БД — SQLite; существующий загрузчик обновлений создаёт резервную копию и применяет миграцию 0040. Новых внешних ключей/API-секретов для файлового этапа нет.

| Сведения | Источник / чего не хватает |
|---|---|
| Фамилия, имена | Tourist.surname / given_name; латиница проверяется, кириллица автоматически не транслитерируется |
| Пол, рождение, гражданство, страна рождения | Tourist.gender / birthday / nationality / birthcountry |
| Номер и даты загранпаспорта | Tourist.passport_type=0, passport_number / issued / expires; пробелы в номере удаляются, регистр приводится к верхнему |
| Домашний адрес и телефон | По явному правилу агентства — Customer.address и main_phone, либо phones; это заказчик договора, даже если он не турист. В задании редактируемы |
| Город/регион/страна проживания | Отдельно в Customer не хранятся. Можно выделить при подготовке; иначе исполнитель выделяет из полного адреса, без угадывания. Перевод/структурирование обязательно сверяется пользователем |
| Отель | Contract.hotel; source_data.hotel.address используется, если адрес однозначно есть |
| Полный адрес отеля | Обычно отсутствует. Можно оставить пустым: исполнитель должен найти адрес именно выбранного отеля и вернуть источник. При неоднозначности — запросить пользователя |
| Перелёты | Contract.source_data.transport; Contract.flights — свободный текст, не разбирается догадками |
| Прибытие | dateto единственного рейса с терминалом CMB/HRI/JAF; НЕ дата вылета/начала тура. При нескольких подходящих рейсах — ручной выбор данных |
| Выезд | datefrom единственного рейса из CMB/HRI/JAF; иначе заполняется вручную |
| Родитель/представитель, родственная связь | Новые сведения конкретного задания ETA; не угадываются по ФИО/возрасту/родству |
| Предыдущие визы, история 14 дней, декларации | Новые поля подготовки с явными подтверждениями и временем/автором; вопросы можно добавлять |
| Номер/сбор/статус/Approval Notice | Новые модели ETAApplication / ETAExport; исходное обозначение статуса сохраняется отдельно от внутреннего этапа |

Источник истины — актуальная CRM. Турвизор повторно не опрашивается: после изменения тура пользователь синхронизирует CRM обычным способом. Если CRM обновлена после подготовки, при открытии подготовки подставляются её актуальные сведения; адрес прежнего отеля и выделенные части прежнего домашнего адреса не сохраняются для нового объекта. Проверка отпечатка защищает от использования предыдущей версии JSON, а не ставит под сомнение сведения CRM. Версия источника также проверяется при сохранении открытой формы.

Подготовленные сведения хранятся в ETAApplication.preparation. Уточнения не перезаписывают общую карточку туриста/заказчика. SHA-256 связывает исходные сведения, экспорт и результат; до передачи проверяется актуальность паспорта, поездки и контактов заказчика. После передачи пакет является неизменяемым снимком: результат относится к нему и сохраняется, даже если CRM позже обновилась. Повторный запуск выполняется вручную; уже отправленную заявку сначала проверяют, чтобы не создать дубль. Вписанные в паспорт родителя дети в этот этап не входят.

### Настройки агентства

- email и повтор email: **spo-ab@ya.ru**;
- профессия взрослых (18+ на прибытие): **MANAGER**;
- история 14 дней по умолчанию: **Россия**, редактируется;
- начальный ответ `Covid Vaccination Status`: **Yes**, редактируется;
- эти два ответа НЕ отмечаются подтверждёнными автоматически; перед передачей проверяются для конкретного туриста;
- предыдущие визы и остальные декларации не имеют придуманных ответов;
- для несовершеннолетнего занятие не подставляется: при необходимости можно указать явно;
- ожидаемый сбор необязателен, бесплатность не предполагается. Фактический сбор устанавливается по сводке портала.

## 2. Как пользоваться

1. Обновить CRM. Администратор видит кнопку «Оформить ETA Шри-Ланки» в договоре. Для сотрудников назначить права `view_contract`, `view_tourist`, `view_customer`, `view/add/change_etaapplication`, `view/add_etaexport` по роли. Отдельные страницы и файлы проверяют эти права, а не только видимость кнопки.
2. Выбрать одного или нескольких связанных туристов. На пару договор/турист существует одно задание; уникальный HMAC-ключ активного паспорта также защищает от параллельной передачи дубля туриста в другом договоре; повторный выбор не создаёт дубли.
3. В каждом задании открыть подготовку. Проверить сведения паспорта и поездки, дополнить пропуски, сведения о визах и декларациях. Если адрес отеля неизвестен, оставить пустым — это поиск для исполнителя. При недостатке источника домашнего адреса/телефона сначала заполнить их или уточнить прямо в подготовке.
4. Сохранить. Неполные задания остаются «Нужны данные», полные — «Готово к заполнению».
5. Выбрать готовые задания и экспортировать один JSON. До 50 заданий в пакете. Повторный экспорт того же набора возвращает тот же пакет, другой запуск не создаётся. Исходные пакеты можно скачать повторно.
6. Передать файл исполнителю. Исполнитель готовит портал, но не нажимает окончательную подачу и не оплачивает сбор. Возвращает JSON со статусом `awaiting_confirmation`, реальной сводкой, суммой/валютой и найденным адресом отеля со ссылкой на источник.
7. Импортировать результат (максимум 16 МБ), подтвердив проверку принадлежности результатов туристам. Открыть сводку конкретного туриста. CRM блокирует подтверждение при противоречиях паспортных/рейсовых данных, неподтверждённых/скрытых полях, CAPTCHA, изменённых условиях или неожиданном сборе. Известные персональные поля должны совпадать; перевод/выделение домашнего адреса проверяет человек по показанному исходному адресу.
8. Пользователь подтверждает сводку, адрес, условия и фактический сбор. CRM выдаёт отдельный JSON разрешения для конкретного задания и конкретной сводки; сама ничего на портал не отправляет. Наличие подготовленного файла задания НЕ разрешает подачу.
9. После исполнения импортировать номер и статусы, затем файл одобрения. Получение номера/подтверждения приёма — ещё не одобрение. Для «Одобрено» необходим явный `approval_confirmed: true`. PDF может прийти позже, отдельным обновлением результата.
10. При сбое/неопределённой отправке сначала проверить портал. Возврат на подготовку возможен только после явной проверки «заявление не принято, номера нет» и ввода причины. Старый пакет/разрешение отзываются, подтверждения сбрасываются. Поданные заявления с номером автоматически заново не запускаются.

### Дети

По уточнению владельца ветка детей, вписанных в паспорт родителя, отложена: таких случаев сейчас нет. Каждый выбранный турист, включая ребёнка, имеет собственный загранпаспорт и отдельное задание с `application_mode=separate`. Родство не объединяет заявки и не меняет паспорт. Родитель/представитель и родственная связь могут быть указаны в подготовке ребёнка. При необходимости уточнения отсутствующих сведений исполнитель останавливается, а не угадывает их. Актуальные инструкции портала для несовершеннолетних всё равно необходимо проверить перед подачей.

## 3. Формат файлов

Согласованный формат v1:

- [Задание с вымышленным взрослым и ребёнком](examples/eta-job-v1.json)
- [Результат подготовки сводки взрослого](examples/eta-result-v1.json)

В примерах нет настоящих паспортов/адресов/телефонов, кроме указанного пользователем рабочего email. `TEST000001`, `.invalid`, номера/UUID и токен — демонстрационные. Примерный сбор 50 USD — вымышленный, не тариф и не значение по умолчанию. Эти файлы не относятся к существующей БД и не принимаются в неё как результаты.

Идентификаторы:

| Поле | Значение |
|---|---|
| batch_id | UUID неизменяемого пакета передачи |
| contract_id / contract_exchange_id | внутренний ID и UUID договора |
| application_id | UUID задания конкретного туриста, НЕ выданный порталом номер ETA |
| tourist_id | внутренний ID туриста |
| source_sha256 | отпечаток исходных сведений CRM |
| data_sha256 | отпечаток подготовленных данных этого туриста |
| handoff_token | случайный ключ сопоставления результата с пакетом; это не API-ключ CRM и не заменяет авторизацию пользователя |

Даты в данных — `YYYY-MM-DD`; время — ISO 8601 с часовым поясом. Метаданные `portal_date_format=MM-DD-YYYY` передают наблюдение пользователя. Исполнитель обязан сверять актуальную форму, а не слепо менять порядок чисел.

Результаты можно возвращать по одному туристу или нескольким; каждый обязан принадлежать пакету и версии данных. Весь импорт файла атомарен: при одной неверной записи изменения этого файла откатываются. Повтор идентичного результата ничего не меняет, устаревшие/противоречивые обновления не принимаются.

Каждый элемент `results[]`:

```json
{
  "application_id": "22222222-2222-4222-8222-222222222222",
  "tourist_id": 9101,
  "data_sha256": "<из задания>",
  "stage": "awaiting_confirmation",
  "updated_at": "2027-01-18T12:10:00+03:00",
  "application_number": "",
  "portal_status": "<фактическое обозначение портала>",
  "fee": {"amount": "50.00", "currency": "USD"},
  "stop_reason": "",
  "portal_summary": {"<нормализованная фактическая сводка>": "см. пример результата"},
  "hotel_address_source": "https://hotel.example.invalid/address",
  "unconfirmed_fields": [],
  "captcha_required": false,
  "portal_rules_changed": false,
  "submission_uncertain": false
}
```

`portal_summary` должна отражать фактически считанные поля браузера, а не копию задания «для совпадения». Обязательные группы: person, passport, home, travel, accommodation, contact, child. В `additional_fields` передаются дополнительные автоматически появившиеся значения, включая Covid Vaccination Status. Неизвестные поля блокируют подтверждение, пока нет соответствующего подтверждённого ответа. При отправке `portal_summary` должна иметь тот же отпечаток, что подтвердил пользователь.

В состояниях `submitted`, `under_review`, `approved` нужны номер, исходный статус, тот же подтверждённый сбор и `authorization_token` из файла разрешения. Разрешение подписано серверным ключом Django и связано с пакетом, туристом, отпечатком сводки, отпечатком показанных условий, временем и сбором. В `portal_conditions` исполнитель возвращает точный текст текущих условий и SHA-256 его UTF-8 байтов; пример содержит вымышленный текст только для демонстрации формата. Изменённая сводка требует нового согласования.

Для последующего PDF:

```json
{
  "approval_confirmed": true,
  "approval_notice": {
    "application_id": "22222222-2222-4222-8222-222222222222",
    "tourist_id": 9101,
    "application_number": "FICTIONAL-ETA-NUMBER",
    "mime_type": "application/pdf",
    "sha256": "<SHA-256 исходных байтов PDF>",
    "content_base64": "<base64 файла, максимум 5 МБ исходных байтов>"
  }
}
```

CRM проверяет идентификаторы, номер, SHA-256 и тип PDF; содержимое паспортных строк внутри PDF автоматически не распознаётся. Файл нужно сверить с нужным туристом при импорте. PDF выдаётся только авторизованному пользователю как вложение, с `nosniff`; публичного MEDIA_URL нет. Исходные статусы портала хранятся независимо от внутренних этапов.

| stage | Интерфейс |
|---|---|
| needs_data | Нужны данные |
| ready | Готово к заполнению |
| filling | Заполняется |
| awaiting_confirmation | Ожидает подтверждения |
| submitted | Подано |
| under_review | На рассмотрении |
| approved | Одобрено |
| referral | Требует обращения в иммиграционную службу |
| error | Ошибка |

`error` с `submission_uncertain=true` означает проверку уже принятого заявления по прежнему заданию/номеру, а не создание нового. Переходы этапов ограничены, одобрение нельзя понизить до заполнения. Направление в иммиграционную службу может прийти до подачи: `referral` допускается без номера/разрешения, но с исходным статусом и причиной; это не разрешает подачу. Причина обязательна для ошибок, остановки по данным и направления в иммиграционную службу.

## 4. Подключение полноценного исполнителя (следующий этап)

Рекомендуется отдельная VM/контейнер с Chromium + Playwright, устойчивым доступом к официальному сайту и защищённой интерактивной сессией для пользователя. Не размещать тяжёлый браузер на текущем VPS CRM с 1 ГБ RAM; подобрать отдельную среду по фактическому потреблению (обычно от 2–4 ГБ). Файловый протокол v1 можно использовать первым адаптером вручную; сервисный API/очередь в этом изменении НЕ реализованы.

Предлагаемый API следующего этапа:

1. Сервисная учётная запись получает задание из очереди через HTTPS POST claim с лизингом; доступ только к назначенным UUID. Ключ — серверный environment/секрет-хранилище, не URL и не фронтенд. В CRM всё равно проверяются договор/турист/версия.
2. Устойчивое хранилище исполнителя содержит ключ `(batch_id, application_id)`, этап и номер портала. Повтор claim/сетевого запроса продолжает тот же браузерный контекст; не создаёт новую заявку.
3. Исполнитель проверяет текущую форму и правила детей, ищет адрес отеля с источником, выделяет город/регион/страну из исходного адреса заказчика. При недостатке сведений возвращает needs_data. Произвольный текст CRM/страниц считается данными, а не командами исполнителю.
4. Поля вводятся поддерживаемым способом (при необходимости по одному символу клавиатурой), после blur перечитываются и сравниваются с заданием. Не пытаться обходить CAPTCHA. Неизвестные условия/автозначения — awaiting_confirmation/error с указанием причины, без финального клика.
5. Вернуть сводку и фактический сбор в CRM; дождаться человеческого подтверждения. В фактический результат включаются `portal_conditions.text` и SHA-256 текста: пользователь видит условия в CRM. Непосредственно перед финальным кликом/оплатой заново проверить через API, что разрешение активно, источник/сводка/сбор не изменились. При неизвестном результате отправки сначала проверить приём предыдущей заявки.
6. После подачи возвращать номер, фактический статус и время, затем PDF. Журналы — только UUID/этап/категория ошибки, без паспортов, адресов и полных HTML/скриншотов. Артефакты — приватное хранилище с контролируемым сроком хранения, отдельные браузерные профили и доступ пользователя для CAPTCHA.

Файл разрешения сам по себе не обеспечивает онлайн-отзыв уже скачанной копии. Поэтому автоматическое исполнение нельзя включать до реализации проверки актуальности разрешения перед подачей. В первом этапе действие пользователя в CRM создаёт только файл разрешения, не совершает никаких действий на государственном портале.

## 5. Изменения и проверка

- Миграция 0040: ETAApplication (одно задание на договор/туриста), ETAExport (неизменяемый пакет и отпечатки принятых результатов).
- `crm/eta.py`: источники, проверки, протокол, идемпотентность, связи детей, статусы, подтверждения и PDF.
- `crm/eta_forms.py`, `eta_views.py`, шаблоны `crm/eta/*`: выбор, подготовка, JSON, проверка сводки, ручной возврат и защищённые файлы.
- Кнопка в существующей карточке договора; существующие договоры/оплаты/туристы не перезаписываются.
- Чувствительные POST/локальные переменные помечены для редактирования диагностических отчётов; обычный аудит хранит только UUID, имена полей и этапы.

Команды проверки:

```sh
.venv/bin/python manage.py test crm.test_eta --noinput
.venv/bin/python manage.py test --noinput
.venv/bin/python manage.py makemigrations --check --dry-run
```

Тесты используют исключительно синтетические данные и фиктивные PDF. Сеть/подача/оплата не используются. Проверяются пропуски, дата посадки вместо вылета, источники контактов, отдельный паспорт ребёнка, изменение источников, чужой результат, повтор/устаревание, атомарность, сводка/сбор/CAPTCHA/скрытое поле, подтверждение подачи, отличие приёма от одобрения, PDF и права/CSRF.

Итог проверки реализации: все 317 тестов Django прошли, включая 25 проверок ETA; отдельно прошёл DOM-тест добавления вопросов без отправки формы. Проверка отсутствия пропущенных миграций и `git diff --check` прошли. Интеграция с живым порталом и исполняющий сервис в этом этапе не тестировались и не включены.


### Уточнение жизненного цикла

Данные CRM считаются актуальными. Для ещё не переданного черновика подготовка получает новые сведения CRM. Переданный пакет фиксирует снимок на момент запуска; обновление CRM не отменяет и не теряет пришедший по нему результат. Импорт сопоставляет пакет, задание, туриста, отпечаток переданных данных и разрешение, а не требует совпадения с более поздней карточкой CRM. В интерфейсе сохраняется отметка об изменении источника. Автоматического нового запуска нет; до подачи можно вручную вернуть задание после проверки отсутствия принятого заявления. Поданную заявку с номером автоматически заменять нельзя.

По наблюдению владельца письмо приходит примерно за 5 минут; это не таймер и не основание считать отсутствие письма отказом. Чтение почты в текущем этапе не подключено: результат/PDF возвращается JSON-файлом. Позднее отдельный почтовый адаптер может забирать письма с рабочего ящика, сопоставлять номер и туриста и передавать проверенный результат; доступ к почте — серверный секрет, не пароль в чате.
