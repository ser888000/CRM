# Резервные копии и восстановление CRM

Цель владельца: потеря не более суток данных, восстановление за 3–6 часов. Работающий запасной VPS не нужен. Код и службы готовы в репозитории; отправка во внешнее хранилище не включается без настройки и успешной первой проверки.

## Что сохраняется

В SQLite находятся договоры, заказчики, туристы, финансы, задачи, справочники, содержимое Библиотеки и документы ETA. Согласованная копия создаётся SQLite Backup API без остановки приложения; обычное копирование работающего `db.sqlite3` вместо этого использовать нельзя.

«Скачать копию базы» — проверенная SQLite. «Полный архив» — проверенная SQLite, исходники точной установленной версии (`git archive`), `/etc/aborigen-crm.env`, справочные конфигурации Nginx и служб, manifest с SHA-256 каждого файла. Архив не содержит старых бэкапов, временных импортов, SSH-ключей, виртуального Python-окружения и TLS-ключей. Новому серверу нужен новый сертификат. Сейчас файловых полей вне БД нет; при добавлении внешних вложений состав архива необходимо расширить.

GitHub содержит программу, но не рабочие данные и секретные настройки. В полном архиве есть также программа: это дополнительный вариант на случай недоступности GitHub.

Полный скачанный архив НЕ зашифрован и содержит секреты. Доступ к подготовке/скачиванию — только superuser, POST защищён CSRF; файлы доступны только через авторизованное скачивание, не через Nginx static. Хранить на защищённом компьютере. Не присылать в чат и не загружать в GitHub. На VPS хранится одна последняя ручная копия; предыдущая удаляется только после проверки новой. Ранее настроенные `/root/crm-daily-backups` и таймер `aborigen-crm-backup` остаются без изменений.

## Установка кнопок

Обычное обновление через CRM запускает `deploy/install-service.sh`, который устанавливает фиксированную root-службу `aborigen-crm-recovery` и watcher. Веб-процесс передаёт только вид копии и случайный UUID, без команд и путей. Root-служба сама читает приватные настройки; веб-процесс получает готовый архив для передачи администратору и не открывает исходный файл настроек напрямую. Создание выполняется вне HTTP-запроса, работа CRM продолжается.

После обновления: **Справочники и управление → Резервные копии**. Подготовить базу, скачать; затем подготовить полный архив и сохранить на компьютер. Скачивание начнётся по появившейся ссылке. Проверка вручную на сервере:

```sh
systemctl status aborigen-crm-recovery.path --no-pager
journalctl -u aborigen-crm-recovery.service -n 20 --no-pager
```

Подробные тексты исключений и вывод команд с секретами намеренно не записываются. Статусы root-owned, group-readable: `/var/lib/aborigen-crm-recovery`. Не выдавать веб-пользователю права на `/etc/aborigen-crm.env`.

## Внешнее хранилище: существующий Мастерхост

У владельца Windows-хостинг `u340795`, FTP `u340795.ftp.masterhost.ru:21`, около 2,6 ГБ свободно. Это файловое хранилище для копий, не сервер запуска Django. Наличие FTPS ещё не подтверждено. Использовать только explicit FTPS с проверкой сертификата, пассивное соединение; обычный FTP передаёт пароль открыто и не подходит. При отсутствии FTPS/SFTP выбрать другой внешний сервис. Не включать отключение проверки сертификатов.

Используется restic через rclone: restic шифрует содержимое, имена и метаданные; rclone даёт доступ к FTPS. FTP-пароль и пароль шифрования разные. Желательно создать отдельного пользователя, ограниченного каталогом копий вне каталогов сайтов. Тариф не менять до измерения объёма первой копии; 14 ежедневных и 3 ежемесячных точки могут пересекаться. Дедупликация не гарантирует, что всё поместится: сжатый архив меняется. Следить за квотой и расходом трафика. При заполнении новый бэкап завершится ошибкой; старые не удаляются до успешного чтения новой копии обратно.

На VPS, от root:

```sh
apt-get update
apt-get install -y restic rclone
install -d -m 700 /root/.config/rclone /root/.config/aborigen-crm
rclone config
```

В интерактивном мастере создать remote **masterhost**, тип **ftp**, host `u340795.ftp.masterhost.ru`, port `21`, логин отдельного FTP-доступа (либо текущий `u340795`), пароль вводить только в терминале. В расширенных параметрах **explicit_tls=true**, **tls=false** (это флаг implicit TLS; explicit включён), **no_check_certificate=false**. Не сохранять пароль в истории команд. Проверить права:

```sh
chmod 600 /root/.config/rclone/rclone.conf
rclone lsd masterhost:
```

Команда должна работать с настоящей проверкой TLS-сертификата. Если ошибка TLS — остановиться, уточнить hostname/FTPS у поддержки. Листинг не проверяет все операции restic; первая полноценная загрузка/чтение проверит их отдельно.

Создать отдельный пароль шифрования без вывода на экран:

```sh
umask 077
openssl rand -base64 48 > /root/.config/aborigen-crm/restic-password
install -m 600 /opt/aborigen-crm/deploy/masterhost-backup.env.example /etc/aborigen-crm-backup.env
```

Перед инициализацией **сохранить этот пароль вне VPS**: скачать файл через SFTP/SCP на защищённый компьютер и сохранить в менеджере паролей. Для восстановления нужны сам пароль, доступ к FTPS и адрес репозитория. При потере пароля restic восстановление невозможно. Rclone config содержит доступ к FTP (obscured, не полноценное шифрование) — хранить приватно. Доступы не отправлять в чат.

Только для нового пустого каталога `crm-backups`:

```sh
python3 /usr/local/libexec/aborigen-crm-enable-offsite.py --init
```

При продолжении уже существующего restic-репозитория опустить `--init`. Эта команда: проверяет настройки, инициализирует новый репозиторий при явном `--init`, делает первый полный бэкап, скачивает его потоково обратно и сравнивает SHA-256. Только после успеха включает ежедневную отправку в **03:30 Europe/Moscow**. Ошибка настройки не включает новый таймер.

## Альтернатива: S3

Вместо FTPS можно выбрать любого независимого S3-совместимого провайдера; Selectel не требуется. Нужны private bucket, HTTPS endpoint, регион, отдельные Access Key/Secret Key с доступом только к каталогу резервов (list/read/write/delete). Публичный доступ выключен. Удаление требуется для политики хранения restic; это также означает, что скомпрометированный VPS может удалить доступные ему копии. Дополнительная скачанная копия на компьютере защищает от такого сценария; неизменяемое хранилище требует отдельной политики и настройки, здесь не обещается.

```sh
apt-get install -y restic
install -m 600 /opt/aborigen-crm/deploy/s3-backup.env.example /etc/aborigen-crm-backup.env
nano /etc/aborigen-crm-backup.env
```

Заполнить только на сервере. Пароль restic создать и сохранить отдельно как выше. Затем тот же `aborigen-crm-enable-offsite.py --init`. В коде нет привязки к платному провайдеру.

## Контроль и хранение

После успешной первой загрузки:

```sh
systemctl list-timers aborigen-crm-offsite.timer --no-pager
journalctl -u aborigen-crm-offsite.service -n 20 --no-pager
```

В административной странице видны последний результат и время последней проверенной внешней копии. При неудаче последняя успешная отметка сохраняется. Автоматическая email/SMS-рассылка не реализована; проверять страницу регулярно. На локальном VPS внешний архив временный, удаляется после завершения попытки. Шифрование выполняет restic, на VPS во время создания есть приватный незашифрованный временный архив.

Политика `keep-daily 14 / keep-monthly 3` применяется только к `host=aborigen-crm, tag=crm-recovery-v1`, и только после успешной проверки обратного чтения новой копии. Не настраивать отдельное S3 lifecycle-удаление внутренних файлов restic: это повредит репозиторий.

Раз в месяц выполнить `restic check` с окружением из приватного файла (через helper ниже) и периодически учебное восстановление. Время восстановления 3–6 часов — цель, не гарантия до проверки на реальном архиве/сети.

## Восстановление: скачать из внешнего хранилища

На резервной Ubuntu 24.04 установить Python, git, restic и при FTPS rclone. Получить этот репозиторий и восстановить приватные настройки доступа/пароль restic из сохранённой внешней копии. Для FTPS также восстановить remote rclone. Не присылать эти файлы в переписку.

Helper `deploy/restic-command.py` загружает приватное окружение, не выводит секреты; запускается из скачанного репозитория:

```sh
python3 deploy/restic-command.py snapshots
python3 deploy/restic-command.py check
```

Выбрать конкретный snapshot ID, скачать только нужный архив в новый приватный файл:

```sh
umask 077
python3 deploy/restic-command.py dump SNAPSHOT_ID crm-full.tar.gz > /root/crm-full.tar.gz
```

Если команда завершилась ошибкой, файл неполный и для восстановления не подходит. Не запускать отправку пустой CRM в тот же репозиторий.

## Восстановление: проверить архив и развернуть

Входные файлы: полный скачанный архив (из кнопки или restic), проверенная процедура и Ubuntu 24.04. Этап проверки не меняет рабочую базу:

```sh
python3 deploy/restore-recovery.py /root/crm-full.tar.gz --stage /root/crm-restored
```

Новый каталог должен отсутствовать. Проверяются безопасные пути без symlink/hardlink, все SHA-256, формат и целостность SQLite. Будет показан revision программы. Не распаковывать архив неизвестного происхождения вручную от root. Проверка SHA-256 выявляет повреждение; подлинность при получении из внешнего хранилища обеспечивает restic с известным паролем, а не manifest сам по себе.

Обычный путь, на новом сервере без работающей CRM:

1. `apt-get install -y git python3-venv python3-dev build-essential nginx certbot`
2. `git clone https://github.com/ser888000/CRM.git /opt/aborigen-crm` и `git -C /opt/aborigen-crm checkout REVISION` (revision из проверенного manifest). Нельзя вслепую использовать latest вместо сохранённой версии.
3. Создать `/var/lib/aborigen-crm` с mode 700, скопировать проверенный `db.sqlite3` туда, `settings/aborigen-crm.env` — в `/etc/aborigen-crm.env` с mode 600. При замене уже существующего экземпляра сначала остановить его, сохранить его отдельную копию и убедиться, что нет старых WAL/SHM от другой базы. Не подменять работающий SQLite.
4. `umask 022`, в `/opt/aborigen-crm`: `python3 -m venv .venv`, `bash deploy/install-service.sh`. Проверить журнал и `/health/`.
5. До проверки отключить `aborigen-crm-update.path`, `aborigen-crm-cleanup.timer` и внешнее копирование. Отключить/не запускать ETA-исполнитель, почтовые обработчики и другие внешние задания. Службы из `server-reference` использовать для сверки, не активировать автоматически.
6. Настроить Nginx для тестового адреса, HTTPS, `/static/` и proxy на 127.0.0.1:8000. Выпустить новый сертификат, настроить renew hook. Не копировать чужую конфигурацию панели поверх текущего Nginx.
7. Проверить вход, несколько договоров, суммы финансов, заказчиков, задачи, Библиотеку и скачивание документов, выгрузку 1С без повторной загрузки финансов в 1С.
8. Остановить/ограничить старую CRM (если доступна), согласовать точку восстановления, переключить A-запись основного домена. Вести запись только в одну базу. После проверки включить необходимые службы и резервирование, подтвердить новую внешнюю копию.

Если GitHub недоступен: исходники есть в `code.tar.gz`. Использовать helper `deploy/restore-recovery.py --code-only /root/crm-restored/code.tar.gz --stage /opt/aborigen-crm` для безопасной распаковки в новый каталог. Затем инициализировать локальный git, добавить origin GitHub и сделать локальный восстановительный commit с пометкой исходного revision (установщик использует git для прав файлов). Не включать web-update до восстановления доступа к GitHub. Это аварийный путь, его необходимо отдельно проверить перед использованием в работе.

## Что ещё нужно от владельца

- Подтверждение, что FTPS доступен на Мастерхосте, и отдельная папка/FTP-пользователь для копий вне сайтов (или параметры выбранного S3).
- Пароли/ключи вводятся только на VPS, не в чат.
- Сохранённый вне VPS пароль шифрования и доступ к хранилищу.
- Первый фактический запуск, замер занимаемого места, скачивание копии на компьютер и учебное восстановление на отдельном VPS.

Разработка проверена на вымышленных данных. Реальный FTPS/S3, квота и восстановление рабочей базы не проверены без настройки владельцем.
