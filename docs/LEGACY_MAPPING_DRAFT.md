# Сопоставление старой CRM — черновик по реальной схеме

Резервная копия восстановлена в отдельной SQL Server, проверена RESTORE VERIFYONLY и DBCC CHECKDB, включён READ_ONLY. В этой стадии данные в новую CRM не загружались. Персональные значения и статистика рабочей истории в Git не сохраняются.

| Источник | Назначение / замечания |
|---|---|
| COMPANY | Заказчики/контрагенты: ID_COMPANY — исходный ключ, YUR_FIZ — физ./юр. лицо, имя и раздельные ФИО, основные паспортные/адресные поля и примечания. Роли контрагентов требуют сопоставления. |
| LIST_TELEPHONES, LIST_EMAIL_CLIENT | Основные и дополнительные контакты по ID_COMPANY; сохранить все значения, нормализацию использовать для поиска/сопоставления. |
| LIST_REQUIS_FIZ, LIST_REQUIS_COMPANY | Отдельные реквизиты, на которые ссылаются документы. Исторические реквизиты договоров сохранять отдельно от актуальной карточки заказчика. |
| LIST_DOCUMENTS, TIP_DOCUMENTS | Документы разных типов; исходный ключ ID_DOC. Номер не заменяет ключ. Договоры, счета, ПКО и другие документы нельзя автоматически суммировать как независимые продажи. |
| LIST_TOVAR_DOC | Строки конкретного документа: туристы, паспорта, цены, количества, скидки и суммы. Для старых строк не создавать справочник Tourist. Текущая новая модель требует расширения для самостоятельных снимков туриста в строке. |
| LIST_MANYS | Клиентские платежи по ID_MANY с ID_COMPANY / ID_DOC. TRASH=NULL — активная запись. Знак суммы важен: отрицательные значения встречаются даже при направлении «ПРИХОД». Учитывать признак оплаты/планирования, валюту, рублёвую сумму, курс и примечания. |
| LIST_CONTACT_COMPANY, VID_CONTACT, PRIZNAK_CONTACT | Действия/задачи по ID_CONTACT и заказчику. Признак контакта определяет план/выполнение; LIST_STATUS_CONTACT задаёт приоритет. Даты, время, сотрудника, описание и результат необходимо сохранить. Прямую связь с договором не выдумывать. |
| LIST_INFO_BASE | Дерево библиотеки: ID_INFO_BASE, ID_RAZDEL_INFO_BASE (корень -1), заголовок TEMA_NAME и RTF TEXT_INFO_BASE. Сохранить форматированный оригинал; отображение в веб-интерфейсе требует безопасного преобразования. Есть ссылка на отсутствующего родителя, которую нужно отразить в журнале исключений. |
| LIST_ATACH_DOCUMENTS | Реальные бинарные вложения DOC_STREAM и связи с библиотекой, документами, заказчиками. По подтверждению владельца переносить только неудалённые вложения библиотеки; остальные исключить. |
| ADD_SPR_*, LIST_SPR_* и другие справочники | Переносить используемые значения и исходные идентификаторы. Сопоставление по нормализованному названию; не заменять совпадением случайного числового ID новой CRM. |
| SETTING_ADD_FIELDS_MODULE | Подписи пользовательских полей помогают отличить смысл от технического имени; в частности ADD_SUM_OPLATY_TO подписано «Себестоимость». |

## Правила подготовки импорта

- Не изменять источник; все исследования выполнять на восстановленной копии.
- Исходные идентификаторы хранить в отдельном пространстве старой CRM; не подставлять их в tourvisor_id и не сопоставлять с первичными ключами новой базы.
- Подтверждено: корзину, «СЧЕТ» и «ПКО» исключить. Итог ТО — фактически перечисленная сумма за вычетом возвратов, дата означает полный расчёт; без даты сумма промежуточная. Восстановление необходимых удалённых заказчиков для сохранения действующих связей согласовано владельцем; прочую корзину исключить.
- Сверять шапку и строки документов. Расхождение не устранять молча изменением суммы; сохранить оба источника и зарегистрировать исключение.
- Нулевые финансовые записи, платежи без найденного документа и строки без родителя требуют явной обработки, а не случайных связей/выдуманных договоров.
- Реквизиты сотрудников можно использовать для исторического авторства, но не переносить старые пароли, ключи интеграций и настройки авторизации.
- Подготовить синтетические тестовые примеры; реальные записи, вложения, резервные копии и их содержимое не публиковать в репозитории.
