# Обновление CRM из браузера

После первоначальной установки: «Справочники и управление» → «Обновление CRM» либо `/management/update/` → «Установить обновление». Доступно только активным суперпользователям; запрос POST защищён CSRF. Можно закрыть браузер — установку продолжает systemd, страница при повторном открытии показывает последний результат.

## Первоначальная установка на выделенном VPS

```bash
ssh -o ObscureKeystrokeTiming=no root@168.113.171.231
```

```bash
git -C /opt/aborigen-crm pull --ff-only origin main && bash /opt/aborigen-crm/deploy/install-service.sh
```

Установщик создаёт root-owned `/usr/local/libexec/aborigen-crm-update.py`, `aborigen-crm-update.path` и oneshot `aborigen-crm-update.service`. Путь отслеживает `/var/lib/aborigen-crm/update-request.json`. Состояние и журнал: `/var/lib/aborigen-crm-updater/`, root:aborigen-crm, каталог 0750, файлы 0640. Веб-приложение может читать результат, но не менять worker или его состояние. Веб-процесс не получает sudo, доступ к systemctl или запись в checkout.

## Установка и восстановление

1. Веб-приложение атомарно публикует UUID запроса и идентификатор администратора. Команды, ветка, адрес репозитория и пути из HTTP не принимаются. Повторные нажатия не создают параллельный запуск; у worker также есть файловая блокировка.
2. Worker проверяет ожидаемую конфигурацию SQLite (другие БД не обновляет), единственный разрешённый origin `https://github.com/ser888000/CRM[.git]`, чистоту checkout, получает main и допускает только fast-forward. При совпадении версий установка не требуется. Локальные изменения не затираются.
3. Включается режим обслуживания; останавливаются CRM и очистка временных импортов. SQLite backup API сохраняет согласованную базу в `/root/crm-backups/before-web-update-…sqlite3` (0600), до изменения кода и миграций.
4. Выполняются fast-forward и штатный `deploy/install-service.sh`: зависимости, миграции, справочники, static, проверки и службы. Секреты из `/etc/aborigen-crm.env` сохраняются. `/health/` проверяет загрузку Django и доступность БД, возвращая только `ok`/503.
5. Если установка после остановки завершилась ошибкой, worker пытается вернуть прежний commit, согласованную копию базы, прежние зависимости/static и запустить CRM. Режим обслуживания исключает пользовательские записи между установкой и откатом. При успешном откате результат остаётся «обновление не установлено», с объяснением восстановления.
6. При неудачном восстановлении или обнаружении прерванного обновления (например, после выключения VPS) режим обслуживания сохраняется. Повторный запуск из браузера блокируется до диагностики. Резервные копии не удаляются автоматически.

Во время остановки Gunicorn Nginx может возвращать 502/503. Страница повторяет проверку и показывает результат после запуска. Журнал в браузере ограничен последними 24 КБ, вставляется текстом; значения типовых секретов и пароль в URL маскируются. Запрос записывается в AuditEvent с администратором. Обновления устанавливаются по нажатию, не по расписанию.

## Диагностика при ошибках

На VPS: `systemctl status aborigen-crm-update.path aborigen-crm-update.service --no-pager`, `journalctl -u aborigen-crm-update.service -n 80 --no-pager`, `/var/lib/aborigen-crm-updater/status.json` и `latest.log`. После аварийного выключения сначала проверить checkout, состояние миграций/базы и резервную копию; не удалять maintenance вслепую. Автоматические восстановления не заменяют внешнее резервное копирование.

Проверено локально: права/CSRF, атомарная очередь, повторные нажатия, резервная копия/восстановление SQLite, сбой установки и откат с имитацией команд systemd/git, защита от временных symlink, режим обслуживания, маскирование журнала, синтаксис shell и systemd units. В браузере проверены кнопка и опрос имитированных статусов. Реальная системная служба на VPS запускается владельцем при первоначальной установке; прямого SSH-доступа у агента нет.


## Исправление прав кода после первого запуска обновлятора

Причина инцидента 25.10: UMask=0027 у root worker создавал изменённые Git-файлы 0640 root:root, недоступные пользователю aborigen-crm. Проверка manage.py от root проходила, а Gunicorn завершался с PermissionError при чтении crm/forms.py. Откат Git с той же маской воспроизводил ошибку.

Исправление: worker и установщик используют umask 022 для публичного кода; отдельная утилита восстанавливает 0644/0755 только у отслеживаемых Git-файлов и их каталогов. Неотслеживаемые .env, SQLite, .venv и пользовательские данные не открываются для чтения. Резервные копии и статус/журнал сохраняют отдельные ограниченные режимы доступа. Установщик дополнительно выполняет manage.py check от фактических UID/GID службы CRM.

Для восстановления уже сломанного запуска от root: `umask 022 && git -C /opt/aborigen-crm pull --ff-only origin main && bash /opt/aborigen-crm/deploy/repair-web-update.sh`. Скрипт отказывается работать при активном обновляторе, останавливает службы, исправляет права и переустанавливает код штатным установщиком с резервной копией. База повторно из старой копии не восстанавливается. Маркер обслуживания и запрет кнопки снимаются только после успешного health check. При ошибке выводится журнал Gunicorn и режим обслуживания сохраняется.
