# Первая проверка 1С 7.7

`probe.1c` — авторский модуль внешней обработки: выбирает `exchange.xml`, проверяет версию и выводит договоры, суммы, проекты операций и количество замечаний. Не создаёт и не изменяет объекты базы. Это проверка формата и установленного XMLParser, а не реализация приёмника документов.

`example_plan.json` — полностью вымышленный пример: 100 000 ₽, себестоимость 70 000 ₽, три оплаты картой. Первое строгое превышение себестоимости — 20 января, комиссия целиком 30 000 ₽.

Структура оболочки исследована по предоставленному владельцем `Conv44.ert`. Сборщик `scripts/build_1c_probe.py` принимает именно этот проверенный файл (SHA-256), заменяет его исполняемый модуль полностью, сохраняет остальные потоки и проверяет обратную распаковку. Оригинальный модуль, исходная оболочка и готовый бинарник в репозиторий не включаются. Для сборки нужен Python-пакет `olefile` только в среде сборки; CRM он не требуется.

```sh
python scripts/build_1c_probe.py /private/Conv44.ert /private/CRM_1C_Probe.ert
```

Сборка не является компиляцией или исполнением в 1С. Нужна проверка на компьютере пользователя с 1С 7.7 и V7Plus/XMLParser >= 2.0. Открыть тестовую копию базы, затем Файл → Открыть → CRM_1C_Probe.ert; выбрать XML из подготовленного пакета. Сообщения выводятся в окно сообщений 1С; обработка после проверки закрывается.

Пока в модуле отсутствует создание заявок, путёвок, отгрузок и бухгалтерских операций. Следующий этап после успешного чтения: сопоставление справочников и аналитик в копии, создание одной цепочки, сверка проводок и проверка повторной загрузки. Закрытые годы и вручную введённые документы автоматически не менять.

## Одна заявка в тестовой копии

`application.1c` — следующий самостоятельный модуль. Из XML можно выбрать один договор 2026 года, в том числе из пакета с несколькими договорами. По UUID сначала проверяется наличие заявки. Существующие заявки, включая помеченные на удаление, не изменяются; повторный ключ пропускается. Проверка создания и повторного запуска в настоящей 1С пока ожидается.

Заказчик сопоставляется по нормализованному полному наименованию/ФИО; несколько совпадений требуют выбора. При отсутствии создаётся физическое лицо: полный ФИО сохраняется в `ПолнНаименование`, короткое представление ограничено штатной длиной 1С. Ни паспортные, ни контактные данные не заполняются. ТО выбирается из существующих контрагентов при отсутствии однозначного совпадения. Тур выбирается из существующего справочника; проверяется его принадлежность выбранному ТО. Это обязательная аналитика данной конфигурации 1С. Новые ТО и туры обработка не создаёт.

Одна техническая строка «Туристы» содержит заказчика и полные суммы. При отсутствии такой записи создаётся только ФИО и ссылка на плательщика, без вымышленных пола/даты рождения/паспортов. Для каждой стороны создаётся договор расчётов с именем `CRM <UUID заявки>` под соответствующим владельцем. Новые записи и непроведённая заявка записываются в одной транзакции; повторный поиск UUID выполняется также внутри транзакции. Проверяются сохранённый UUID, суммы и отсутствие проведения. При ошибке транзакция откатывается.

Номер заявки назначается самой 1С. Исходный номер и дата договора CRM сохраняются в примечании; реквизит «Номер туроператора» не используется вместо номера CRM. Путёвка, отгрузка и бухгалтерские операции на этом этапе не создаются. Заявки с нулевой себестоимостью допустимы; отгрузка по ним остаётся отложенной.

В этом модуле больше кода, поэтому для его сборки используется оболочка из предоставленного `FreshOfficeCRM_1.1_1C7.ert`: оригинальный исполняемый модуль заменяется целиком. Никакой код подключения FreshOffice к базе не переносится в новый модуль. Новый профиль сборки:

```sh
python scripts/build_1c_probe.py /private/FreshOfficeCRM_1.1_1C7.ert /private/CRM_1C_Application_v1.ert --application
```

В тестовой копии открыть новую ERT, выбрать уже проверенный реальный XML и один договор. Просмотреть созданную заявку без ручного проведения или сохранения формы, затем повторить загрузку того же договора. Ожидается сообщение, что заявка уже существует, без создания новой и без изменения существующей. Ручное сохранение формы 1С запускает собственную логику конфигурации (в частности, создание «Услуг по заявке»), поэтому проверка первого этапа ограничена просмотром.


### Версия 4: соответствия ТО и фиксированный тур

Для каждого нового UUID туроператора CRM один раз запрашивается действующий контрагент 1С. Выбор сохраняется штатными `СохранитьЗначение`/`ВосстановитьЗначение`, ключ включает каталог информационной базы и UUID ТО. Таким образом настройка относится к этой базе и пользователю 1С, не переносится автоматически между тестовой и рабочей базами. Повторное чтение сохранённого значения проверяется сразу; удалённая, помеченная или устаревшая ссылка требует нового выбора. Изменение названия ТО в CRM не сбрасывает соответствие при том же UUID.

По прямому указанию пользователя тур всегда выбирается автоматически по коду **319** в справочнике «Туры». Ведущие нули кода допустимы; требуется единственный действующий элемент. Нет или неоднозначен — понятное сообщение и остановка до создания заявки. Из тура не подставляется ТО, прежняя проверка принадлежности тура тому же ТО снята: это явное правило пользователя для служебного тура. Перед фиксацией заявки проверяются также сохранённые ссылки ТО и тура.

Уже созданные заявки по-прежнему пропускаются без изменения. Новые настройки следует проверять на ещё не загруженном договоре, затем на другом договоре того же ТО и после повторного открытия обработки. Выполнение новой версии, постоянство настройки между сессиями и подстановка тура 319 требуют проверки в копии пользователя.

## Первая проведённая путёвка

`voucher.1c` собирается отдельным профилем `--voucher` на той же оболочке, что и приложение. В первой версии из пакета выбирается один договор 2026 года с уже загруженной заявкой. Тест ограничен полной оплатой по операциям пакета, без возвратов/зачётов и штрафов. Проверяются дата заявки, рублёвая валюта, курс 1, суммы шапки и единственной строки. Заявки с нулевой себестоимостью допустимы; отгрузка и доход этим модулем не создаются.

Если у заявки уже есть путёвка (включая непроведённую или помеченную), новая не создаётся, существующая не изменяется; выводятся статус и номер. Это сохраняет идемпотентность без перезаписи ручных документов и повторного списания.

При первом запуске запрашиваются действующий вид бланков с номерным учётом, склад, серия нужной длины и начальный номер. Настройки сохраняются штатным профилем 1С по каталогу базы и пользователю. На следующих запусках предлагается использовать их или изменить. Значение счётчика не сбрасывается с годом. В начале создания номер сверяется со всеми существующими путёвками этого вида и серии, независимо от склада и состояния: выбирается не меньше сохранённого и строго больше уже занятого максимального номера. Поэтому возможны пропуски занятых/зарезервированных номеров; переполнение длины номера требует сменить настройки. На экране до создания показан фактически выбранный номер.

Новая непроведённая заявка, созданная приёмником со статусом «Введена», переводится в «Оплата» и проводится штатным модулем 1С для формирования расчётов по счетам ТУР. Уже проведённые заявки со статусом «Оплата»/«Оплачена» не перепроводятся; остальные случаи удерживаются для проверки. Затем создаётся одна путёвка датой заявки с полной суммой и себестоимостью единственной строки заказчика, выбранными бланком/складом/серией/номером и включённым списанием БСО. Она проводится штатным модулем, включающим счёт 006 и туристические расчёты. Заявка и новая путёвка обрабатываются одной транзакцией. При отказе проведения/проверки транзакция отменяется, профиль не продвигается.

После фиксации следующий номер сохраняется в профиле. Профиль не является транзакционным хранилищем; восстановление после разрыва между фиксацией и сохранением профиля обеспечивается сверкой с документами. Поддерживается фактически используемый пользователем монопольный режим 1С; конкурентная многопользовательская загрузка этим прототипом не проверена.

Приход диапазона бланков должен быть датирован не позже даты путёвки. Загрузчик не создаёт фиктивный приход и не отключает проверку остатков. При отказе нужно проверить штатные сообщения 1С. Данный модуль не создаёт отгрузку, финансовые операции клиента или оплату ТО.

```sh
python scripts/build_1c_probe.py /private/FreshOfficeCRM_1.1_1C7.ert /private/CRM_1C_Voucher_v1.ert --voucher
```

Сборка и распаковка модуля проверены локально; компиляция, штатные проводки, уменьшение остатка на один бланк, откат при недостаточном остатке и повторная загрузка должны быть проверены пользователем в отдельной копии 1С.

## Первая отгрузка

`shipment.1c`, профиль `--shipment`, создаёт одну отгрузку 2026 года на основании уже проведённых заявки и единственной путёвки. Пользователь подтвердил автоматическое проведение и отсутствие повторной загрузки путёвок; повторять предыдущий этап перед испытанием отгрузки не требуется.

Дата берётся из проверенного `SHIPMENT_DATE` при статусе `in_period`: первое строгое превышение накопленной оплаты над себестоимостью вычислено экспортом CRM. В строке сохраняются полная сумма договора и вся положительная комиссия, ссылка на путёвку и штатная услуга «Комиссионные путевки». Суммы, даты и строки сравниваются с реальными документами базы. Нулевая себестоимость, возвраты/зачёты или иные случаи, помеченные экспортом как требующие проверки, не создают отгрузку. Первые тесты ограничены рублями/курсом 1, положительной комиссией, отсутствием штрафов и одной полной путёвкой. Источники должны быть проведены; допускаются статусы заявки «Оплата», «Оплачена», «Закрыта».

Важно использовать тот же элемент служебной услуги, который ищет штатный модуль проведения: иначе конфигурация может классифицировать строку как собственную услугу вместо комиссии. Поэтому модуль не предлагает произвольный заменитель, проверяет дубли/пометки/номенклатуру и не редактирует справочники. В договорах расчётов проверяется признак «Комиссия»=1: штатная конфигурация использует его для признания в налоговом учёте именно комиссионной суммы. Само проведение выполняется 1С: счета расчётов, выручка и налоговый учёт берутся из действующей конфигурации.

Существующая отгрузка по заявке (включая непроведённую/помеченную) выводится и не меняется, новая не создаётся. Повторная проверка проводится внутри транзакции перед записью. При отказе штатного проведения/контроля записанных сумм откатывается только новая отгрузка. Заявка и путёвка не перепроводятся, номер/остаток бланков не изменяется. Режима обновления отгрузки по изменённому договору пока нет.

```sh
python scripts/build_1c_probe.py /private/FreshOfficeCRM_1.1_1C7.ert /private/CRM_1C_Shipment_v1.ert --shipment
```

Проверить в копии: первая отгрузка, дата и полная комиссия, штатные проводки 90.1 и налогового учёта, повторный запуск без дубля/повторного дохода. Клиентские платежи ещё не создаются; расчёты с клиентом в 1С будут неполными до следующего этапа. Контейнер/распаковка проверены локально; запуск и правильность проводок требуют реальной 1С пользователя.

## Служебные услуги и пустой статус заявки

Реальный тест отгрузки v2 выявил единственное несовпадение — пустой статус заявки. В модуле формы путёвки этой конфигурации при закрытии переменная нового статуса заполняется при наличии единственной путёвки и ещё одного подчинённого документа, затем присваивается заявке и проводится. Штатная форма заявки создаёт «Услуги по заявке» даже с пустой таблицей. Первые версии приёмника этот служебный документ пропускали, поэтому закрытие путёвки могло сбросить статус и изменить проводки заявки.

Общий авторский фрагмент `application_services.1c` добавляется сборщиком после объявлений переменных в модули заявки, путёвки и отгрузки. Внутри транзакции он добавляет отсутствующий штатный документ без строк и проведения. Существующие услуги не редактируются; дубли/пометка удаления требуют проверки. Application v5 обеспечивает это при создании новой заявки, Voucher v2 — перед новым проведением. Старые заявки по ветке пропуска дубликатов по-прежнему не обновляются.

Shipment v3 допускает временно пустой статус только для восстановления заявки с точным UUID и служебными метками нашего импорта в примечании. Все прочие проверки остаются обязательными. После подтверждения пользователем добавляются отсутствующие служебные услуги и пустой статус восстанавливается на `Оплата` (представление «Частично оплачена»), затем заявка перепроводится штатным модулем. Это восстанавливает расчёты ТУР.3.2, предусмотренные для данного теста. Перед созданием отгрузки повторяется строгая проверка без разрешения пустого статуса. Восстановление и отгрузка обрабатываются одной транзакцией; ошибка откатывает обе операции. Непустые статусы произвольно не заменяются, путёвка не перепроводится, бланк не списывается повторно.

Пользователь отдельно подтвердил, что ручная форма заявки запрашивает статус подтверждения ТО, после чего формируются проводки. Это согласуется с кодом: «Подтверждена ТО» и состояния оплаты создают проводки, пустой статус их не создаёт. Выбран `Оплата`, уже использованный при первом тесте путёвки, а не произвольная смена схемы расчётов.

Контейнер, включение общего фрагмента и обратная распаковка трёх новых обработок проверены. Восстановление пустого статуса и проведение отгрузки ещё требуют запуска Shipment v3 в тестовой копии пользователя.

## Читаемые основания (Application v6)

Пользователь подтвердил выручку/налоговые проводки отгрузки и отсутствие повторного создания; на сравнительном снимке схема совпадает с ручным образцом. Отдельно попросил убрать UUID из основания плательщика, если оно не нужно для связи. Основной ключ обмена хранится в `Заявка.Идентификатор` и служебной метке примечания; отображаемое название договора расчётов не обязано содержать UUID.

Новые основания создаются по штатной формуле конфигурации: `Заявка №<номер 1С без префикса> от <дата>`. Поле основания остаётся заполненным: прямой импорт объекта не должен зависеть от вызова обработчика формы, который заполняет его при ручном вводе. UUID заявки сохраняется для поиска повторной загрузки; старое имя `CRM <UUID>` поддерживается только для обратной совместимости и перехода к читаемому названию.

При выборе уже загруженного договора Application v6 предлагает переименовать связанные основания, только если их имя точно совпадает с прежним `CRM <UUID этой заявки>`. Проверяются владелец, отсутствие пометки удаления, длина и отсутствие другого одноимённого договора у владельца. Если имя уже обычное либо задано вручную, оно не меняется. Изменения двух сторон выполняются одной транзакцией; одна и та же ссылка обрабатывается один раз. При конфликте откат/остановка, без слияния ссылок и без переноса долгов.

Меняется только `Наименование` существующего элемента справочника. Заявка и денежные документы не записываются заново и не перепроводятся, UUID не заменяется. Повторный запуск с уже читаемыми основаниями ничего не меняет. После переименования отчёт движения нужно сформировать заново, чтобы обновить отображение названий. Фактическое переименование в 1С ещё ожидает проверки пользователем; контейнер/распаковка и структура блоков проверены.


27.10.2026: Application v7 снимает запрет переименования импортированного основания при совпадении названия с другой записью. Название не ключ; меняется только текущий элемент, без объединения ссылок и перепроведения. Проверки владельца, метки CRM и транзакция сохранены. Пользователь сообщил о блокировке v6; v7 собран с проверкой CP1251/OLE roundtrip, runtime в 1С ожидается.


## Клиентские оплаты: тестовый приёмник v1 (27.10.2026)

Пользователь подтвердил, что Application v7 переименовал основания везде. Новый `payment.1c` выбирает одну ручную оплату картой/СБП или один зачёт из `OPERATIONS/OPERATION` того же XML. ПКО/РКО пока не создаёт, сообщает об этом явно; их штатный налоговый учёт требует отдельного этапа проверки.

Карты — Дт 57.1 / Кт 62.2; СБП — Дт 57.2 / Кт 62.2; возвраты с отрицательной суммой на тех же счетах.
