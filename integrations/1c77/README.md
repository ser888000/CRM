# Первая проверка 1С 7.7

`probe.1c` — авторский модуль внешней обработки: выбирает `exchange.xml`, проверяет версию и выводит договоры, суммы, проекты операций и количество замечаний. Не создаёт и не изменяет объекты базы. Это проверка формата и установленного XMLParser, а не реализация приёмника документов.

`example_plan.json` — полностью вымышленный пример: 100 000 ₽, себестоимость 70 000 ₽, три оплаты картой. Первое строгое превышение себестоимости — 20 января, комиссия целиком 30 000 ₽.

Структура оболочки исследована по предоставленному владельцем `Conv44.ert`. Сборщик `scripts/build_1c_probe.py` принимает именно этот проверенный файл (SHA-256), заменяет его исполняемый модуль полностью, сохраняет остальные потоки и проверяет обратную распаковку. Оригинальный модуль, исходная оболочка и готовый бинарник в репозиторий не включаются. Для сборки нужен Python-пакет `olefile` только в среде сборки; CRM он не требуется.

```sh
python scripts/build_1c_probe.py /private/Conv44.ert /private/CRM_1C_Probe.ert
```

Сборка не является компиляцией или исполнением в 1С. Нужна проверка на компьютере пользователя с 1С 7.7 и V7Plus/XMLParser >= 2.0. Открыть тестовую копию базы, затем Файл → Открыть → CRM_1C_Probe.ert; выбрать XML из подготовленного пакета. Сообщения выводятся в окно сообщений 1С; обработка после проверки закрывается.

Пока в модуле отсутствует создание заявок, путёвок, отгрузок и бухгалтерских операций. Следующий этап после успешного чтения: сопоставление справочников и аналитик в копии, создание одной цепочки, сверка проводок и проверка повторной загрузки. Закрытые годы и вручную введённые документы автоматически не менять.

## Одна заявка в тестовой копии

`application.1c` — следующий самостоятельный модуль. Из XML можно выбрать один договор 2026 года, в том числе из пакета с несколькими договорами. По UUID сначала проверяется наличие заявки. Существующие заявки, включая помеченные на удаление, не изменяются; повторный ключ пропускается. Проверка создания и повторного запуска в настоящей 1С пока ожидается.

Заказчик сопоставляется по нормализованному полному наименованию/ФИО; несколько совпадений требуют выбора. При отсутствии создаётся физическое лицо: полный ФИО сохраняется в `ПолнНаименование`, короткое представление ограничено штатной длиной 1С. Ни паспортные, ни контактные данные не заполняются. ТО выбирается из существующих контрагентов при отсутствии однозначного совпадения. Тур выбирается из существующего справочника; проверяется его принадлежность выбранному ТО. Это обязательная аналитика данной конфигурации 1С. Новые ТО и туры обработка не создаёт.

Одна техническая строка «Туристы» содержит заказчика и полные суммы. При отсутствии такой записи создаётся только ФИО и ссылка на плательщика, без вымышленных пола/даты рождения/паспортов. Для каждой стороны создаётся договор расчётов с именем `CRM <UUID заявки>` под соответствующим владельцем. Новые записи и непроведённая заявка записываются в одной транзакции; повторный поиск UUID выполняется также внутри транзакции. Проверяются сохранённый UUID, суммы и отсутствие проведения. При ошибке транзакция откатывается.

Номер заявки назначается самой 1С. Исходный номер и дата договора CRM сохраняются в примечании; реквизит «Номер туроператора» не используется вместо номера CRM. Путёвка, отгрузка и бухгалтерские операции на этом этапе не создаются. Заявки с нулевой себестоимостью допустимы; отгрузка по ним остаётся отложенной.

В этом модуле больше кода, поэтому для его сборки используется оболочка из предоставленного `FreshOfficeCRM_1.1_1C7.ert`: оригинальный исполняемый модуль заменяется целиком. Никакой код подключения FreshOffice к базе не переносится в новый модуль. Новый профиль сборки:

```sh
python scripts/build_1c_probe.py /private/FreshOfficeCRM_1.1_1C7.ert /private/CRM_1C_Application_v1.ert --application
```

В тестовой копии открыть новую ERT, выбрать уже проверенный реальный XML и один договор. Просмотреть созданную заявку без ручного проведения или сохранения формы, затем повторить загрузку того же договора. Ожидается сообщение, что заявка уже существует, без создания новой и без изменения существующей. Ручное сохранение формы 1С запускает собственную логику конфигурации (в частности, создание «Услуг по заявке»), поэтому проверка первого этапа ограничена просмотром.
