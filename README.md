# АБОРИГЕН-ТУР · CRM

Первая рабочая версия внутренней CRM туристического агентства. Django 5.2, Python 3.12, PostgreSQL 16. Это среда разработки, ещё не публичный сервис для рабочих персональных данных.

## Запуск без Docker

```bash
cd /workspace/CRM
python -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed_templates
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver 0.0.0.0:8000 --noreload
```

Без POSTGRES_HOST используется локальная SQLite для разработки. Для PostgreSQL задайте POSTGRES_HOST, POSTGRES_DB, POSTGRES_USER и POSTGRES_PASSWORD. Пароли не добавляйте в Git.

Путь `/` — таблица договоров; `/tasks/` — задачи; `/admin/` — вход и редактирование карточек. Создавайте отдельную учётную запись для каждого сотрудника. Администратор имеет полный доступ; будущим сотрудникам выдавайте группы разрешений. Ограничение доступа по отдельным договорам пока не реализовано.

## Docker Compose (разработка)

Создайте игнорируемый `.env` с POSTGRES_PASSWORD и DJANGO_SECRET_KEY (собственные случайные значения), затем:

```bash
docker compose up --build -d
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py test
```

PostgreSQL хранится в томе pgdata. Не используйте `docker compose down -v`, если нужно сохранить данные. Веб-порт привязан к loopback. Compose запускает сервер разработки, а не production deployment. Для публикации нужны HTTPS, DJANGO_DEBUG=0, DJANGO_SECRET_KEY, разрешённые хосты, сборка/раздача staticfiles, Gunicorn и резервное копирование с проверкой восстановления.

## Основной сценарий

1. Создайте заказчика и ТО в разделе управления.
2. Создайте договор: текущая дата, внутренний ID автоматически; внешний номер заполняется отдельно.
3. Добавьте строки с туристами или общей стоимостью тура. Отрицательные строки уменьшают стоимость.
4. Выберите шаблоны задач. При отсутствии даты тура соответствующая задача не создаётся, показывается предупреждение. Перед сохранением доступны отдельные сроки каждой задачи; настройки смещений — в справочнике шаблонов. Дополнительные задачи можно выбрать и при редактировании договора.
5. В финансах зарегистрируйте поступления клиента и оплаты ТО. Возвраты — отдельные положительные суммы с соответствующим типом операции.
6. Проверьте итоги договора: стоимость, оплачено, долг, себестоимость, управленческий доход.
7. Список задач позволяет переносить одну или несколько незавершённых задач на дату; прежний и новый сроки сохраняются в истории.

Задачи могут быть без клиента/договора. Ежедневные, еженедельные, ежемесячные и ежегодные повторы создаются сразу на выбранное количество дат (1–366). Для отсутствующего дня месяца используется последний день месяца.

Копирование договора доступно действием в списке управления. Переносятся параметры и строки, но не номер Турвизора, оплаты, брони, задачи или отметка полной оплаты ТО. Даты поездки и срок оплаты ТО копируются: перед сохранением проверьте их.

## Проверки

```bash
.venv/bin/python manage.py check
.venv/bin/python manage.py test
```

Тесты проверяют возвраты, частичные оплаты, копирование, отсутствие повторных задач, массовый перенос с историей, ограничения доступа, месячные повторы и создание задач через форму договора.

## Следующие этапы / ограничения

- Интеграция Tourvisor пока не реализована. Подтверждены ограничения API: нет платежей, реквизитов договора и уведомлений об изменениях. Не регистрировать webhook без отдельной проверки существующего подключения.
- В таблице сейчас основные колонки и фильтры; все поля доступны в карточке. Полные фильтры по любому полю, сортировка и серверные настройки таблицы — следующий этап. Порядок/видимость колонок пока сохраняются в текущем браузере отдельно для пользователя.
- Есть справочники ТО, типов договоров, способов оплаты и шаблонов задач; остальные классификаторы пока текстовые.
- Индивидуальные сроки автозадач доступны до сохранения. Пересчёт уже созданных задач при изменении поездки и Telegram-сводка остаются следующими этапами.
- История фиксирует изменения карточек и финансов и переносы задач. Для строк договора пока фиксируется факт сохранения; полная история старых/новых значений строк и их удаления ещё необходима.
- Нет бухгалтерского регистра, декларации УСН, обмена с СБИС, импорта старой базы, вложений и production deployment.
- Паспортные данные при изменении карточки могут попадать в историю. Доступ к истории выдавайте только уполномоченным сотрудникам; политика хранения и защита данных должны быть определены до загрузки рабочей базы.

В облачных задачах используйте существующий checkout: отдельный Git worktree не нужен. Сервисы после восстановления среды необходимо запускать заново.

## Пакет улучшений от 22.10.2026

Полный план сохранён в docs/PLAN.md. Финансы доступны прямо в договоре: добавить строку в блоке «Финансы по договору», затем сохранить договор. В общем списке финансов отображается заказчик. В отдельной форме платежа выбор заказчика отбирает его договоры; заказчика можно пропустить и сразу выбрать договор по номеру.

Шаблон ссылки на бронь задаётся в карточке ТО: `https://operator.example/booking/{booking}`. У каждого ТО собственный формат ссылки; подставляется URL-кодированный номер. Указанные ранее индивидуальные ссылки сохранены как запасной вариант, если шаблон не задан. В договоре и задачах отображается кнопка перехода. Для несвязанной задачи ТО и номер брони можно указать вручную.

Сроки автозадач настраиваются в «Шаблоны задач»: опорная дата, смещение в днях и порядок. Перед сохранением договора можно выбрать задачи и изменить каждый срок. Даты по умолчанию не раньше даты договора; если несколько задач попадают на один день, они создаются в порядке шаблонов. Заданный вручную срок сохраняется. Рейсы копируются в описание задач по флагу шаблона. Уже созданные задачи повторно не создаются и не переносятся без действия пользователя.

Для обновления VPS остановите runserver, сделайте резервную копию SQLite, затем выполните `git pull --ff-only origin main`, `.venv/bin/python manage.py migrate`, `.venv/bin/python manage.py check` и запустите сервер снова. Миграции переносят существующие текстовые справочники; курс округляется до двух знаков по правилу ROUND_HALF_UP. Обратный переход через эти миграции не поддерживается: для отката потребуется восстановление резервной копии вместе с соответствующей версией кода.
