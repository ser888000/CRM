# Постоянный запуск на выделенном тестовом VPS

Это установка для одного выделенного Ubuntu VPS по уже согласованному SSH-сценарию. CRM слушает только 127.0.0.1:8000; публичное размещение и HTTPS настраиваются отдельно. Nginx не меняется, внешние порты не открываются. Служба работает от системного пользователя aborigen-crm, не от root. Один worker и два потока рассчитаны на тестовый VPS с 1 ГБ RAM.

## Первая установка

1. Подключиться по SSH, убедиться, что приглашение начинается с root@crm-test. Остановить runserver клавишами Control+C.
2. Из /opt/aborigen-crm сделать копию db.sqlite3, затем обновить код.
3. Выполнить `bash deploy/install-service.sh` от root. Скрипт создаёт пользователя, случайный секрет Django в /etc/aborigen-crm.env (0600), переносит SQLite через SQLite backup API в /var/lib/aborigen-crm/db.sqlite3, применяет миграции, собирает статические файлы и устанавливает службу. Существующая база в /var/lib никогда не заменяется старой копией из checkout. Перед миграциями создаётся резервная копия в /root/crm-backups. SECRET_KEY изменится при первом переходе — потребуется повторный вход в браузере.
4. Для ключа Tourvisor выполнить `.venv/bin/python deploy/set-tourvisor-key.py`. Значение вводится скрыто и не попадает в историю shell. Затем `systemctl restart aborigen-crm`.

Облачные секреты Codex автоматически на VPS не переносятся. Не записывайте ключ в Git и не передавайте в чат. Скрипт редактирует только запись TOURVISOR_API_KEY, сохраняя остальные настройки.

## Проверка и просмотр

`systemctl status aborigen-crm --no-pager`

`curl -I http://127.0.0.1:8000/admin/login/`

На Mac в отдельном окне: `ssh -o ObscureKeystrokeTiming=no -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -N -L 18000:127.0.0.1:8000 root@168.113.171.231`. Браузер: локальный порт 18000. Туннель нужен для просмотра, но остановка туннеля не останавливает CRM. При необходимости диагностика: `journalctl -u aborigen-crm -n 40 --no-pager`. Не пересылайте журналы без проверки на персональные данные.

## Последующие обновления

`cd /opt/aborigen-crm && git pull --ff-only origin main && bash deploy/install-service.sh`

Для простого перезапуска: `systemctl restart aborigen-crm`. Для остановки: `systemctl stop aborigen-crm`.

После перехода активная база — /var/lib/aborigen-crm/db.sqlite3. Не запускайте обычный runserver или migrate с прежними настройками: это откроет старую базу checkout. Все миграции сервиса выполняет install-service.sh с его окружением. Для ручной команды задавайте CRM_DATABASE_PATH явно. Храните резервные копии отдельно от сервера; автоматическое внешнее резервирование и проверка восстановления ещё необходимы до рабочей эксплуатации.

## Пределы проверки

В среде разработки проверены миграции, тесты импорта, Gunicorn при DEBUG=0 и выдача статических файлов. Установка пользователя и запуск systemd на VPS выполняются владельцем сервера по инструкции; доступ к VPS у агента отсутствует. Скрипт не выполнялся на чужом рабочем сайте.

## Вход по публичной HTTPS-ссылке

Для выделенного VPS 168.113.171.231 добавьте DNS A-запись crm.aborigen-tour.ru на этот адрес, без AAAA. Затем от root выполните `bash deploy/install-https.sh`. Скрипт проверяет DNS, устанавливает Caddy из Ubuntu, настраивает автоматический TLS и проксирование на loopback, включает безопасные cookies и HTTPS в Django. Сохраняет копию файла окружения в /root; базу и ключ Tourvisor не меняет. При занятом другим сервером 80/443 останавливается до установки. Если UFW активен, добавляет разрешения 80/443; внешний firewall провайдера должен также пропускать эти порты. Для сертификата порты должны быть доступны из интернета.

Открыть https://crm.aborigen-tour.ru и войти существующей учётной записью. В «Справочники и настройки → Пользователи → Добавить» создать отдельного пользователя. Для супруги с полным доступом включить «Активный», «Статус персонала» и «Статус суперпользователя». Пароль вводит владелец в HTTPS-форме; его не передавать в чат. Для будущих сотрудников назначать ограниченные права через группы.

После включения HTTPS использовать доменную ссылку: прежний HTTP-вход через туннель перенаправляется на HTTPS. Последующие обычные обновления install-service.sh сохраняют публичные настройки. Проверка сертификата: `curl -I https://crm.aborigen-tour.ru/admin/login/`. Диагностика TLS: `journalctl -u caddy -n 30 --no-pager`.

### Если на VPS уже установлен Nginx

Используйте `bash deploy/install-nginx-https.sh` вместо установщика Caddy. Создаётся отдельный сайт /etc/nginx/sites-available/aborigen-crm; остальные сайты сохраняются. До выпуска сертификата HTTP обслуживает только ACME-проверку, остальные запросы получают 404. Certbot получает сертификат через webroot; затем включаются HTTPS-прокси и перенаправление HTTP, настройки Django переключаются на public_settings с сохранением секретов. Включается certbot.timer и deploy-hook перезагрузки Nginx после продления. Регистрация ACME без email; состояние продления проверяйте через systemctl status certbot.timer и certbot renew --dry-run. Финальная проверка curl должна вернуть HTTP 200 страницы входа. Скрипт проверен на синтаксис в среде разработки; выпуск сертификата и systemd выполняются на VPS.

## Локальное распознавание паспортов

После обычного обновления выполните `bash deploy/install-ocr.sh` один раз: установятся Tesseract и языки rus/eng, Python-зависимости и перезапустится служба. Кнопки доступны в карточке договора для заказчика и туристов. Изображения JPEG/PNG обрабатываются локально во временном каталоге, распознанные поля возвращаются для проверки без записи в БД. Ограничение: 6 МБ, 16 мегапикселей, 42 секунды; в стандартном одном worker обрабатывается одно изображение за раз. Обновление install-service.sh теперь также устанавливает зависимости из requirements.txt.

## Очистка предпросмотров группового импорта

install-service.sh устанавливает и включает aborigen-crm-cleanup.timer (ежечасно с задержкой до пяти минут). Его oneshot-служба запускает `manage.py purge_tourvisor_batches` от aborigen-crm с существующим EnvironmentFile и доступом только к /var/lib/aborigen-crm для записи. Истёкшие исходные снимки очищаются, пакеты старше семи дней удаляются; договоры и их финансы не удаляются. Проверка: `systemctl status aborigen-crm-cleanup.timer --no-pager`.


## Обновление из браузера

Штатный install-service.sh также устанавливает отдельный root worker и aborigen-crm-update.path. После одной ручной установки новые версии можно ставить через «Справочники и управление → Обновление CRM». Подробности, границы проверки и диагностика: [WEB_UPDATES.md](../docs/WEB_UPDATES.md). Веб-приложение root-права не получает.

## Проверка HTTP/2 на существующем Nginx

При нестабильной загрузке через отдельные сети HTTP/2 может уменьшить количество TLS-соединений браузера, объединяя запросы страницы в одно соединение. Это не гарантирует устранение потерь/фильтрации при самом TLS-рукопожатии. Принудительный TLS 1.2 также уже давал тайм-аут во внешней проверке; не следует объявлять TLS 1.3 единственной причиной.

Для выделенного сайта `/etc/nginx/sites-available/aborigen-crm` подготовлен отдельный инструмент:

```sh
python3 deploy/enable-http2.py
python3 deploy/enable-http2.py --apply
```

Без `--apply` файл не меняется. Применение требует root: проверяются конфигурация и наличие HTTP/2-модуля; исходный файл копируется в `/root/crm-nginx-backups/`; меняются только SSL `listen` порта 443; затем выполняются `nginx -t` и плавный `systemctl reload nginx`. При ошибке проверки/перечитывания исходный файл возвращается на диск. Изменение не запускается автоматически обычным обновлением CRM. Версии TLS, сертификат, БД, Gunicorn, firewall, MSS и MTU инструмент не изменяет. Целевая конфигурация — установленный Nginx 1.24 из Ubuntu.

Проверка после применения на VPS:

```sh
curl --http2 --resolve crm.aborigen-tour.ru:443:127.0.0.1 -I https://crm.aborigen-tour.ru/health/
```

Ожидается `HTTP/2 200`, если локальный curl собран с HTTP/2. Внешний доступ и телефон проверяются отдельно. Откат — скопировать указанный инструментом файл резервной конфигурации обратно в `/etc/nginx/sites-available/aborigen-crm`, проверить `nginx -t`, затем выполнить `systemctl reload nginx`.

TLS 1.0 и 1.1 не включать. Текущий установщик сохраняет TLS 1.2 + 1.3 и добавляет HTTP/2 для новых установок. Временное ограничение только TLS 1.2 в этой утилите не выполняется. После сетевой диагностики 30–31.10.2026 прежние временные изменения MSS/MTU отменены пользователем, службы active, локальный health HTTP 200. HTTP/2-инструмент подготовлен и проверен четырьмя автономными тестами; на рабочем VPS он ещё не запускался.

## Внешние резервные копии и скачивание администратором

`install-service.sh` устанавливает `install-recovery.sh`: отдельный root worker и watcher для безопасной фоновой подготовки SQLite/полного архива. В админке появляется «Резервные копии». Внешний таймер по умолчанию выключен; обычное обновление не подключает платное хранилище и не затрагивает существующий локальный ежедневный бэкап.

Состав архива, FTPS Мастерхоста через restic/rclone, альтернативный S3, приватные настройки, первая проверяемая загрузка и порядок восстановления: [docs/RECOVERY.md](../docs/RECOVERY.md). Внешний архив шифруется restic; пароль обязательно хранить вне VPS. Ручной скачанный архив не зашифрован и содержит секреты.
